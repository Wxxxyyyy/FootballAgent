## 一、意图判断与分类

这个项目同时服务两个目标，所有组件需求都能归入其一:

| 意图 | 内容 | 判断标准 |
|------|------|---------|
| **A. 生产可靠性** | 赛前预测必须准时、可靠地推到手机 | 断了用户立刻受损 |
| **B. 工程深度展示** | 面试能讲清楚的架构完整性（MQ/CI/版本管理…） | 缺了不影响运行，但影响"讲" |

第一性原理推论: **A 类组件永远排在 B 类前面**。本周两次真实事故（6/30 Bark 丢件、7/2 赛前 1.5h 推送丢失 + 字段不匹配导致置信度 N/A）全部属于 A 类，而路线图原稿把大量精力排给了 B 类。

## 三、分阶段计划

### 🔴 P0 — 保住核心承诺（本周，A类）

> 原则: 让"赛前收到预测"这件事在机器重启、网络抖动、服务崩溃时依然成立，或至少"断了马上知道"。

| # | 任务 | 做法 | 工作量 |
|---|------|------|--------|
| 0.1 | **提交今天的修复** | 当前 notifier重试/llm_predictor/prediction_api 修复还在工作区未提交，先 commit 打 tag（v1.2） | 10min |
| 0.2 | **8000 服务守护** | systemd unit（Restart=always + After=docker）替代 nohup；日志落 journald/文件 | 0.5天 |
| 0.3 | ~~自建 bark-server 容器~~ **（2026-07-02 评估后放弃）** | 自建需对公网开 8088 端口，带来"公开推送中转"滥用风险 + 运维负担，收益仅为送达可靠性。权衡后改为: 继续用公共 api.day.app + notifier 4次重试/退避/失败告警。已删除 bark-server 容器与相关配置，零公网暴露。若后续仍频繁丢件再回头自建。 | 已闭环 |
| 0.4 | **告警闭环（最小可用）** | 复用 Bark 通道推"系统告警"分组: ①调度 tick 失败 ②/api/predict 5xx ③推送最终失败 ④8000 健康检查失败（cron 每5分钟 curl /health）。不引 Prometheus，先用最笨可靠的方式 | 1天 |

**验收标准**: 拔电重启整台机器 → 全部服务自动恢复 → 下一场比赛四档推送照常到手机；任一环节挂掉 → 5分钟内手机收到系统告警。

### 🟡 P1 — 数据闭环与提效（下周，A/B混合）

| # | 任务 | 做法 | 工作量 |
|---|------|------|--------|
| 1.1 | **启用 Redis 容器并真正接入** | `docker-compose up -d redis`；接入三处真实场景: ①预测结果缓存（同一 match_id+触发档 不重复算）②推送/触发去重状态从文件迁到 Redis（现在是 json 文件）③懂球帝/titan007 请求缓存 | 1天 |
| 1.2 | **赛后准确率自动跟踪** | 比赛结束后从 titan007 抓实际比分，与 data/predictions/ 对比，累计 accuracy/Brier 落 MySQL；每周日推一条"本周预测战绩"到手机 | 1-2天 |
| 1.3 | **LLM 评测最小闭环** | 基于 1.2 的数据: LLM最终判断 vs 纯ML vs 蒙特卡洛 三者准确率对比表——回答"LLM到底有没有增益"这个核心问题 | 1天 |

**面试讲点**: 预测系统的评估不是离线跑分，而是生产环境持续回流（prediction → outcome → metric）。

### 🟠 P2 — 工程质量与架构完整性（第3-4周，B类）

| # | 任务 | 做法 | 工作量 |
|---|------|------|--------|
| 2.1 | **契约测试优先的测试体系** | 本周字段不匹配事故（llm_predictor 输出 vs notifier 读取）就是缺契约测试。优先写: ①llm_analysis 输出 schema 测试 ②notifier 渲染测试 ③_normalize/_fallback 单测 ④odds 提取测试；再补 Text2SQL 安全防线等存量模块 | 2-3天 |
| 2.2 | **CI（GitHub Actions）** | push/PR: ruff + pytest；先不设覆盖率门禁（避免为凑数写测试），跑通后再逐步收紧 | 0.5天 |
| 2.3 | **RabbitMQ 事件驱动改造** | 启用 compose 里的 rabbitmq；改造为: OpenClaw 采集→发消息（odds_update/match_result/daily_matches）→消费者: 入库/触发预测/失效缓存；带死信队列。**注意**: 当前规模（每天几场比赛）HTTP 直连完全够用，此项价值主要是 B 类（架构展示），所以排在 P2 而非 P0 | 2-3天 |
| 2.4 | **observability/ 激活或删除** | LangFuse tracer 真正挂到 LLM 调用上、用量统计落 Redis；如果决定不用就删掉死代码（面试被问到"这模块谁在用"答不上来更糟糕） | 1天 |

## 四、和原路线图的差异（为什么这样改）

| 原路线图 | 本计划 | 理由 |
|---------|--------|------|
| 阶段1 先做 MQ | MQ 降到 P2 | 当前吞吐（日均几场）用不上 MQ 的解耦/削峰，先修真实断点 |
| 无服务守护项 | P0 systemd | 8000 是 nohup 裸进程，这是当前最大单点 |
| 无推送可靠性项 | P0 自建 bark-server | 本周两次真实丢件，核心承诺的最后一米 |
| 测试目标"覆盖率>70%" | 契约测试优先，不设初期门禁 | 本周事故证明: 覆盖率数字不如关键契约有测试 |
| Prometheus 在阶段5 | 降到 P3 | Bark 告警通道已存在且到手机，最小告警闭环先行 |
